# Web Studio JSON 预览边界

**状态**: 已实现并验证。
**范围**: Playground 中通过目录树或 URL 打开 JSON 文件的元数据恢复、加载与渲染行为。

---

## 问题本质

Playground URL 只保存文件 URI。当前页面根据 URI 重建选中文件时，把 `sizeBytes` 和修改时间置空；因此标题显示 `- · -`，且 2 MiB 自动读取闸门无法判断文件是否过大。

大 JSON 随后可能被完整读取并一次性生成大量高亮 DOM。首次渲染结束不代表可交互：滚动或选择文本仍可能阻塞页面。

因此这不是单一的“高亮慢”问题，而是两段链路共同失效：

1. URI 恢复没有得到可靠的文件元数据。
2. JSON 预览没有把“加载内容”和“生成高亮”拆成两个受控动作。

## 已同意的边界

1. 若 PR 声明 `Fixes #3588`，必须同时修复元数据恢复和 JSON 安全渲染；只改渲染只能声明 `Related to #3588`。
2. 元数据恢复修复位于 Playground 的共享文件选择链路，对所有文件类型生效。
3. 展示策略只修改 JSON：默认显示 beautified plain text，高亮由用户手动触发，且保持只读、可撤销。
4. 复用现有 `fetchFsStat`、2 MiB 阈值和 highlight.js；不新增服务端接口或前端依赖。
5. 新增状态只控制 JSON 预览和高亮；所有文件的可修改性判定保持原样。

## 建议的最小状态流

1. 页面仅有 URI 时，先通过现有 stat API 恢复文件条目。
2. 已知大小且不超过 2 MiB：自动加载，默认展示 beautified plain text。
3. 已知大小超过 2 MiB，或 stat 失败导致大小未知：不自动读取，等待用户显式加载。
4. 内容已加载后，用户可手动切换只读高亮；关闭后回到 plain text。

## 当前不做

- 服务端渲染、分块读取、流式 JSON parser、分页或虚拟化 plain text。
- 为 JSON 以外的代码文件重做预览策略。
- 大 JSON 在线编辑。
- 为尚未测量的任意文件大小承诺“永不崩溃”。

## 决策记录

### D1：大文件与未知大小文件何时读取

**状态**: Confirmed

**推荐**: 不自动读取。先展示文件元数据和“加载格式化文本”按钮；用户点击后完整读取并显示 beautified plain text，高亮仍需第二次手动触发。

理由：修复 `sizeBytes` 后继续沿用自动读取，会让 2 MiB 闸门失去意义；完全禁止预览又违背用户查看大 JSON 的目标。显式加载是复用现有链路的最小安全边界。

### D2：大文件手动加载是否扩展到其他文本格式

**状态**: Confirmed

**推荐**: 只为 JSON 提供“加载格式化文本”入口。Markdown、日志、代码等其他大文件继续沿用现有的“不自动读取”行为。

理由：当前有复现数据和渲染方案的只有 JSON。扩展到所有文本格式会同时引入 Markdown 渲染、代码编辑器和未知格式的性能边界，超出 #3588 的根因修复范围。

### D3：本次性能承诺覆盖多大的 JSON

**状态**: Confirmed

**推荐**: 只承诺已复现的两个量级：约 460 KB 文件保持原有自动加载；约 3.35 MB 文件改为显式加载，加载后可滚动和选择文本，手动高亮可开启和撤销。不对任意大小 JSON 作保证，也不新增未经数据验证的第二个大小阈值。

理由：本次已有这两个真实样本。承诺任意大小会迫使方案升级为分块读取或流式解析；另加一个拍脑袋的硬上限也没有依据。

### D4：stat 失败时是否改变现有错误体验

**状态**: Confirmed

**推荐**: 不改变。仅在选中文件缺少元数据时复用现有 stat 能力补全；stat 失败则保留 URI 和未知元数据，不增加新的错误页或重试机制。未知大小 JSON 仍按 D1 等待用户显式加载。

理由：本次根因需要区分“大小已知”和“大小未知”，不需要把临时 stat 失败升级成新的页面状态。内容读取若也失败，继续沿用现有读取错误处理。

### D5：手动加载后的大 JSON 是否允许编辑

**状态**: Confirmed

**决定**: 手动加载只放开预览和高亮。所有文件的可修改性必须维持原行为：以前允许的仍允许，以前不允许的仍不允许；加载状态不得改变“编辑”按钮的可见性或写回权限。

理由：查看和写回是不同风险边界。若复用“已加载”状态直接开启编辑，会意外绕过现有编辑边界，也会把性能修复扩大为写回设计。

### D6：手动加载入口放在哪里

**状态**: Confirmed

**决定**: 当前页面只有“大文件已跳过”提示，并不存在加载按钮。本次只在 JSON 的该提示旁新增一个“加载格式化文本”按钮；不增加弹窗，不移动标题栏按钮，也不改变其他文件的空状态或操作区。

理由：D1 必须有一个显式入口。复用现有跳过提示所在位置，是唯一必要的 UI 增量，也不会让“加载”和“编辑”混在一起。

### D7：点击加载后是否引入新的处理链路

**状态**: Confirmed

**推荐**: 不引入。按钮只允许现有完整读取与 `beautifyJson` 链路执行；合法 JSON 继续格式化，解析失败继续回退原文。不开 Web Worker，不做流式 parser、分页或新的大小分级。

理由：问题是现有读取与渲染缺少用户闸门，不是缺少第二套 JSON 处理器。先用真实 3.35 MB 样本验证现有 plain-text 链路即可。

## 最小验收清单

1. 目录树选择与 URL 直达均能恢复已有文件大小和修改时间，不再无条件显示 `- · -`。
2. 约 460 KB JSON 保持原有自动加载，默认显示 beautified plain text。
3. 约 3.35 MB JSON 在点击前不读取内容；提示旁只新增“加载格式化文本”按钮。
4. 点击后复用现有完整读取和 `beautifyJson`；可滚动、选择文本，页面不崩溃。
5. “高亮 / 纯文本”可手动切换，高亮保持只读。
6. 所有文件的编辑按钮可见性与写回权限和原来相同。
7. 非 JSON 大文件、stat 失败与内容读取失败的行为保持原样。

## 验证结果

2026-07-28 在本地 `ov-server` 与 Web Studio 开发服务器上验证：

1. 459,835 字节 `beam_topology.json` 自动加载，标题显示 `449.1 KB` 与修改时间，保留原有“编辑”按钮；未出现手动加载按钮。
2. 3,352,293 字节 `drawing_text.json` 初始只显示 `3.2 MB`、修改时间、跳过提示和“加载格式化文本”按钮。
3. 大文件手动加载耗时约 0.79 秒；plain text 为单个无 `<code>` 子节点的 `<pre>`，格式化后约 629 万字符。
4. plain text 滚动响应约 25 ms；全选约 629 万字符耗时约 0.53 秒，页面未崩溃。
5. 459,835 字节样本手动高亮后生成 `code.hljs` 和 82,886 个 token `<span>`；页面中无 CodeMirror，切回纯文本后高亮节点归零。
6. 浏览器错误日志为空；前端测试 82/82、lint、生产构建均通过。
